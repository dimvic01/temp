Yes. I’d restructure this into reusable workflows, with a clear separation between:

    CI/build — runs on main and release/*

    artifact promotion — promotes an already-built image without rebuilding

    local deployment — can deploy a selected image on demand

    cloud deployment — reserved as a future workflow

    feature branches — run the complete build/test/deploy cycle locally, but do not publish to GHCR

One important design point: your current workflow uses GHCR as both the build artifact store and the deployment source. For feature branches, if you want deployment to happen entirely on the local machine, I would build the Docker image directly on the self-hosted runner rather than push a feature-branch image to GHCR.

For main/release/*, build once, publish once, then promote that exact immutable image.

3. Promote

For example:

That guarantees that what you release is exactly what you built/tested.

I'd make deployment a separate workflow_dispatch workflow with inputs such as:

That lets you deploy main or a release independently from the build.
One change I'd make to your current design

I would not use:

TAG="${{ github.ref_name }}"

as the primary artifact identity.

Branch names are mutable. Instead, use the Git commit SHA as the immutable image identity:

ghcr.io/org/app:sha-abc1234

Then use human-friendly tags as aliases:

main
release-1.2.0

For example:

                     ┌── main
                     │
commit abc1234 ──────┼── sha-abc1234
                     │
                     └── release-1.2.0

All three can point to the same image digest.

build-deploy-local.yml

For feature branches, I would avoid GHCR entirely.

name: Build and Deploy Local

on:
  workflow_call:

env:
  IMAGE_NAME: dv-app1

jobs:
  build-deploy:
    runs-on: self-hosted

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.26'
          cache: true

      - name: Validate
        run: |
          go vet ./...
          go test -v ./...

      - name: Build local image
        run: |
          docker build \
            -t "${IMAGE_NAME}:${GITHUB_SHA}" \
            .

      - name: Deploy local
        run: |
          export IMAGE_TAG="${IMAGE_NAME}:${GITHUB_SHA}"

          docker compose up -d --remove-orphans

      - name: Cleanup
        run: |
          docker image prune -f

Your docker-compose.yml would then use:

services:
  dv-app1:
    image: ${IMAGE_TAG}

Promotion workflow

This is where I'd make the architecture more robust.

.github/workflows/promote.yml

name: Promote Image

on:
  workflow_dispatch:
    inputs:
      source_tag:
        description: 'Existing image tag'
        required: true
        type: string

      release_tag:
        description: 'New release tag'
        required: true
        type: string

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  promote:
    runs-on: ubuntu-latest

    permissions:
      packages: write

    steps:

      - name: Login to GHCR
        uses: docker/login-action@v4
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Pull source image
        run: |
          docker pull \
            "${REGISTRY}/${IMAGE_NAME}:${{ inputs.source_tag }}"

      - name: Tag release image
        run: |
          docker tag \
            "${REGISTRY}/${IMAGE_NAME}:${{ inputs.source_tag }}" \
            "${REGISTRY}/${IMAGE_NAME}:${{ inputs.release_tag }}"

      - name: Push release image
        run: |
          docker push \
            "${REGISTRY}/${IMAGE_NAME}:${{ inputs.release_tag }}"

So you could do:

source_tag = sha-a1b2c3d
release_tag = release-1.2.0

and get:

sha-a1b2c3d
      │
      ▼
release-1.2.0

without rebuilding.

3. Why GITHUB_TOKEN works

GitHub automatically provides:

GITHUB_TOKEN

to the workflow.

You don't create it manually.

This:

${{ github.token }}

is the same built-in token and is what we're using for:

docker login ghcr.io

The caller grants it:

permissions:
  packages: read

so the deployment workflow can pull the private GHCR image.

Your three workflows should therefore have:

build-and-publish.yml
    packages: write
          │
          ▼
       GHCR

promote.yml
    packages: write
          │
          ▼
       GHCR

deploy-local.yml
    packages: read
          │
          ▼
       GHCR

So don't create a GHCR_TOKEN. Remove that requirement from deploy-local.yml. The error you're seeing is coming from the workflow definition, not from your GitHub account lacking a secret.
